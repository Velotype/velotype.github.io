Known limitations

  • Request bodies are decoded only when your page sent them. The extension keeps the bytes of a VSON or VBIN body sent with fetch, XMLHttpRequest, or navigator.sendBeacon while the VeloJSON panel is open, so a request made before the panel opened, or by a worker or the browser itself, is listed but not decoded. Chrome's network API gives a request body only as UTF-8 text, which would show corrupted bytes for a binary body, so the panel does not use it. A form post cannot send VSON or VBIN as binary anyway. Use the manual decode tool for those bytes. Response bodies are always decoded, because Chrome says whether they are base64
  • The event trace starts when you press Start, and keeps the last 1,000 events. It needs velotype 0.3.2 or later, and the registration table works with earlier versions
  • VSON and VBIN detection on the network tab uses the Content-Type. velojson has a content type for each format, so the extension trusts it: a body with another content type is never guessed at from its bytes, and a body with one of these content types always shows its real decoding error. Use the manual decode tool for a body with no content type, such as application/octet-stream
  • VBIN is decoded in the debug format, with KeyIDs as keys. The real field names come from a schema's mapper, which the extension cannot know for an arbitrary site. See VeloJSON
